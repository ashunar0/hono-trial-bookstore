# Questions

設計書を読んでもわからなかったこと。止まらずに、おすすめの方で進めた。機能は「入荷のお知らせ」。

## restock ドメイン（段 1）

- QUESTION: 送り先のメールアドレスをどこから読むか。「ドメイン」タブは「宛先は客の email」とあるが、`restock_alerts` の列に email が無く、客の表（Better Auth の user）はどのドメインの表でもない。restock の queries が user 表を読むと「表は 1 つのドメインだけが持つ」に触れそうだった。おすすめの方で進めた: 登録のとき `currentUser.email` を `restock_alerts.email` に写して持つ（注文の行が題名と値段を写すのと同じ形）。cron にはセッションが無いので、持っていないと読む先が無い。登録したあとにアドレスを変えた客にも、登録したときのアドレスに届く。user 表を読む形にするなら、設計書に「auth の持ち物として読む」と書いてほしい。
- QUESTION: POST の確かめる順番。設計書は「在庫があれば 409、本が無ければ 404、待っている登録が既にあれば 200」とだけで、順番がない。おすすめの方で進めた: 404（本が無い）→ 待っている・送信中の登録があればそれを 200 で返す → 在庫があれば 409。登録したあと cron が拾う前に在庫が入った客が、もう一度押しても 409 にならず、同じ登録が返る（2 回目は何度押しても同じ、という設計書の文を優先した）。登録が無い客だけが 409 になる。
- QUESTION: 同時に 2 回登録が来たときは、一意制約（待っている・送信中の行だけ `(customer_id, book_id)`）で止めて、負けた方は勝った登録を読み直して 200 で返す。設計書は「2 回目は 200」とだけで同時の場合を書いていなかったので、そう読んだ。
- QUESTION: 取り消し（DELETE）で、待っている登録が無いときの 404 は、本が無い場合も同じ。本の有無を先に見る段は作らなかった（客の登録が無ければ、どちらでも 404）。取り消しの最中に cron が送信中にしたときは、削除が 0 行で終わるので読み直して 409 にする。同じ客が同時に 2 回取り消したときの負けた方は 404。
- QUESTION: 「送れなかった」の日時。`sent_at` は「送った日時」の列なので、failed の行は null のままにした。締めた日時の列は足さなかった（設計書の列のまま）。
- QUESTION: 待っている登録のレスポンスの列。設計書にない。おすすめの方で進めた: `id・bookId・status・createdAt・sentAt`。email と試した回数は中の都合として返さない（注文の `earnId` などと同じ扱い）。

## 送る（段 3）

- QUESTION: sendRestockAlert の入力。設計書の 1 は「読んだ状態と回数のときだけ切り替え」で、cron の表は拾うものを 3 つ（在庫が戻った待ち／送信中で 3 未満／送信中で 3）に分けているが、usecase が 3 つあるのか、どの状態と回数を渡すのかは書いていない。おすすめの方で進めた: 入力は `{ id, now }` だけ。usecase が自分で読み直し、その読んだ状態と回数で切り替える（grantOrderPoints と同じ形）。3 つの場合分けは usecase の中で決める（送信中で回数が 3 なら送らずに「送れなかった」）。cron は待ちの在庫が戻ったものと、送信中の全部を渡すだけ。
- QUESTION: 「拾った時点で在庫がまた 0 なら送らずに待つ」は、拾う側（cron）と usecase のどちらか。おすすめの方で進めた: 両方。cron は在庫が 1 以上の本の待ちだけを拾う（在庫が 0 の古い登録が毎回の 100 件の枠を食って、戻った本の登録が拾われなくなるため）。usecase も待ちのとき在庫を読み直し、0 なら何も書かずに `waiting` を返す（cron が拾ってから usecase が読むまでの間に売り切れたとき）。送信中のものは在庫を見ない。
- QUESTION: 在庫が戻った本の探し方。待っている本の id を重複なしで全部読み（待っている期間の長い順）、50 冊ずつ inventory の `stocksOf` に聞いて、戻っている本の待ちを古い順に 100 件まで集める。D1 は 1 回の問い合わせに結べる値の数が少ないので、50 ずつにした。待っている本の数が何万にもなると、毎回全部読むのは重いが、今の大きさでは足りる。
- QUESTION: メールを呼ぶのが例外を投げた（失敗の結果ではなく）とき。「呼ぶ前に送信中と回数を書く」ので、例外でも 1 回に数えられ、次の回が同じキーで送り直す。cron は 1 件の例外で止めず、最後にまとめて失敗を返す（sweep-orders と同じ）。
- QUESTION: 送る本が消えている場合（本の削除 API は無いので起きないはず）は、`throw` にした。登録の外部キーが守っている。
- QUESTION: 本番の mailer。「擬似。送ったものを集めるだけ」だが、モジュールの上に配列を持てないので、本番の既定は `console.log` に書くだけの `logMailer` にした。集めるのは `collectingMailer(outbox)`（テストが配列を渡す）。冪等キーは、集める側がキーごとに 1 通だけ持つ形で真似ている（相手の側で防ぐ、の代わり）。置き場所は `src/lib/mailer.ts`。
- QUESTION: メールの失敗は `Failure` の `kind: "upstream"`（`MAIL_NOT_SENT`、502）にしたが、HTTP には出ないので API のエラー表には載せていない。
- QUESTION: cron の式は sweep-orders と同じ `*/15 * * * *`。`wrangler.jsonc` の `triggers.crons` には 1 つだけ書いた（同じ式を 2 回書く必要は無く、`hnk prepare` も通った）。Workers は式が合う cron を全部動かし、片方の失敗がもう片方を止めない。
- QUESTION: 送信中の登録を先に読んでから、待ちを読んで、続けて送る。失敗したメールがその回のうちにもう一度試されないため（3 回の失敗が 3 回の cron にまたがる、という設計書の「3 回失敗したら」の読み方）。

## 設計書の気づき

- 「概要とルール」の技術スタックの表が hono-kit 0.16.0 のまま。リポは 0.17.0（`package.json`）。
- inventory に `restocks`・`restock_lines`（返品の在庫を戻した記録）という表があり、今回のドメイン名 `restock` と紛らわしい。コードの置き場所は別（`inventory` が持つ）なので動くが、読むときに混ざる。どちらかの名前を直すなら、表の方（`stock_returns` など）がよさそう。inventory の usecase にも `restock` がある。
- 「ドメイン」タブの restock の行は「book（本があるか、メールの題名）・inventory（在庫が 1 以上か）」。実際には `findBook`（登録で本があるか、送るとき題名）と `stocksOf`（登録と送るときの在庫）。inventory → book の向きがあるので循環は無い。
